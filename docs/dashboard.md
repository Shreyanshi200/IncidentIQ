# Dashboard

The IncidentIQ dashboard is a separate React application in `apps/dashboard`. Its **Overview** keeps service, environment, and integration coverage uncluttered. Its **Investigations** view lets an operator filter saved automatic incidents and open a dedicated evidence timeline.

## Security model

The static dashboard files have no embedded API key or tenant data. The page sends the operator's separate `read` key once to `POST /v1/dashboard/session`. The API validates the key and returns an eight-hour session cookie with `HttpOnly` and `SameSite=Strict`; production HTTPS also adds `Secure`.

The raw read key is not stored in browser storage. JavaScript cannot read the session cookie, a refresh can safely restore the dashboard, and signing out clears the cookie. Revoking the underlying read key also invalidates its sessions.

Never paste an `ingest` key into the dashboard. An ingestion key can write events; a read key can only load its tenant's dashboard overview, investigations, incident details, and reports.

The server's `INCIDENTIQ_SESSION_SECRET` is different from both API keys. It signs browser cookies, stays only on the API server, and is never pasted into the dashboard.

| Credential | Created with | Used by | Stored where |
| --- | --- | --- | --- |
| Ingestion key (`iiq_...`) | `keys create --scope ingest` | SDKs and integrations that send evidence | Producer secret manager; only its hash is in IncidentIQ |
| Read key (`iiq_...`) | `keys create --scope read` | Operator opening the dashboard | Operator password manager; only its hash is in IncidentIQ |
| Session secret | `openssl rand -base64 48` | API signing dashboard cookies | API server environment only |

## Run it locally

Complete the [getting-started setup](getting-started.md) first. PostgreSQL and the API must be running.

In one terminal, start the API:

```sh
pnpm api
```

In a second terminal, create a read-only key. Copy the `iiq_...` value when it is printed; it cannot be shown again.

```sh
pnpm incidentiq keys create --scope read --tenant local --label local-dashboard
```

In a third terminal, start the dashboard development server:

```sh
pnpm dashboard
```

Open this address in your browser:

```text
http://localhost:5173
```

Paste the read key and select **Open dashboard**. The dashboard development server proxies `/v1` requests to `http://localhost:3000`, so the API and dashboard work together without enabling browser CORS. Refreshing the page restores the secure session for up to eight hours; **Sign out** ends it immediately.

For local use, `INCIDENTIQ_SESSION_SECRET` is optional. If it is unset, the API creates a temporary secret at startup, so restarting the API signs out existing dashboard sessions.

## What the overview means

- **Services** groups accepted evidence by stable service name. It lists each environment, source, event count, and most recent event time.
- **Environments** counts the services and evidence recorded for each environment.
- **Evidence source activity** shows every source that has delivered evidence, such as `node_sdk`, `github_actions`, `kubernetes`, or `alertmanager`. Application-generated signals, including custom health events, use `node_sdk`. The reserved `internal` source is displayed as **IncidentIQ system events** and should only represent lifecycle evidence generated by IncidentIQ itself. A green dot means at least one event was received in the last 24 hours; a yellow dot means IncidentIQ has no recent evidence. This is delivery visibility, not a provider health check.

Use the separate **Investigations** view to list saved incidents for this tenant, including automatically detected incidents. Filter by service, environment, or evidence source, then select **Inspect** to see the precise ordered evidence stored for that incident.

An incident opens only after IncidentIQ accepts an `error` or `critical` event. Follow the [automatic incidents guide](automatic-incidents.md) to create one locally, then return to the dashboard and select **Refresh**. If a section is empty, IncidentIQ has not received matching evidence for that tenant yet.

## Investigate an incident

1. Select **Investigations** in the dashboard navigation.
2. Use the filters in **Incident evidence** to narrow to the service, environment, or source you are investigating.
3. Select **Inspect** on an incident. It opens a dedicated investigation view and updates the browser address to that incident.
4. Use the incident tabs instead of scrolling through one long page. **Analysis** contains the deterministic brief, competing candidates, and validation plan. **Evidence** contains the complete ordered timeline and raw attributes. **AI Review** contains the optional cited second opinion.
5. Start in **Analysis**. The investigation brief is derived from the stored timeline and explains the leading hypothesis, observed scope, supporting factors, counterevidence, and alternative candidate scores. Fixture descriptions and other author-provided scenario text are not shown or sent to AI as evidence. Candidate points prioritize investigation; they are not probabilities.
6. Follow the **Validation plan** before taking remediation action. Its checks use recorded details such as route, version, commit, pod, workload, dependency, and trace when those fields are available. Selecting linked evidence switches to the Evidence tab and focuses the cited event.
7. Open **Evidence** to read the timeline. Each entry has a plain-language summary plus its observed time, source, workload, version, and trace. Important identifiers—including full pod resources—are visually highlighted wherever they appear in the brief, checks, AI review, and timeline. Expand **View raw evidence attributes** to verify the original stored fields. Use the `?` legend beside the timeline heading to check the evidence colours.
8. Select **Download report** to save a tenant-scoped, navigable PDF containing an executive summary, compact incident reasoning, candidate ranking, service propagation, validation plan, optional AI summary, and the complete chronological timeline. Exact event IDs and raw attributes remain in the dashboard to keep the report readable. Treat the file as operational data and store or share it only in an approved location.
9. Treat the displayed leading cause and confidence as an explainable hypothesis. IncidentIQ uses deterministic rules and will mark ambiguous evidence with low confidence; it does not claim proof of root cause.

When the API server has optional AI explanations configured, select **Generate AI explanation** for a cited second opinion. The generated panel is visually labeled, cites only event IDs from the current timeline, and does not replace deterministic ranking or recommended checks. It is cached for the current evidence and included in a PDF generated afterward. See [Evidence-bounded AI explanations](ai-explanations.md) before enabling it, because the selected incident evidence is processed by OpenAI.

The dashboard first displays the 25 most recently active incidents that match the filters. Select **Load 25 more** to continue through the list. Each follow-up page uses a cursor based on the last incident already shown, so newly arriving incidents do not cause duplicates or move a previously loaded result. It does not yet support acknowledgement, resolution, assignment, or free-text search.

When nearby incidents in the same tenant and environment have shared traces or a recorded dependency failure, the Analysis tab shows **Cross-service evidence**. It combines trace and dependency observations into one compact row per service relationship. Exact cited events remain available on demand, while the Evidence tab keeps the complete ordered timeline. The PDF report contains the same evidence-backed propagation section. See [cross-service correlation](cross-service-correlation.md) for matching rules and boundaries.

Each tab has a stable address ending in `/analysis`, `/evidence`, or `/ai-review`. Refreshing the browser or using **Refresh** reloads the same incident and selected tab, as long as the read-key browser session is still valid. Older incident links without a tab continue to open Analysis.

For a meaningful walkthrough, use the 20-event `production-checkout-regression` fixture in the [automatic incidents guide](automatic-incidents.md#rehearse-a-production-like-investigation). It includes a release, route failures, alerts, pod degradation, rollback, and recovery instead of only two demo events.

## Deploy it with the production API

Build the static files from the same released repository version as the API:

```sh
pnpm --filter @incidentiqhq/dashboard build
```

The generated files are in `apps/dashboard/dist`. Serve those files from the same HTTPS hostname as the API and proxy `/v1` to the API container. Keeping both on one origin avoids CORS configuration and lets the dashboard use its protected endpoints safely.

Follow the [production API deployment guide](deployment/api-production.md#6-deploy-the-dashboard) for the exact upload, Nginx, read-key, verification, upgrade, and rollback steps.
