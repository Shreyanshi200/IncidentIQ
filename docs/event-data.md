# Event data guide

IncidentIQ stores normalized events. Each record combines values generated by IncidentIQ, values configured by the integrator, and metadata supplied at runtime by the event source.

## Reading a GitHub Actions deployment event

For the earlier example record with `repository: "acme/orders"`, `run_id: "42"`, and `commit_sha: "abc123"`:

| Field | Origin | Meaning |
| --- | --- | --- |
| `event_id` | Generated by the Action | A new UUID for this exported event; it is not GitHub's run ID. |
| `occurred_at` | Generated at Action runtime | The Action's current time when it builds the deployment event. |
| `received_at`, `created_at` | Generated by the API/database | When IncidentIQ accepted and stored the event. |
| `tenant_id`, `service`, `environment` | Configured in workflow YAML | Values selected by the integrator; IncidentIQ does not infer them. |
| `source` | Action constant | Always `github_actions` for this integration. |
| `event_type` | Action constant | Always `deployment` for this integration. |
| `severity` | Derived from deployment status | `info` for success; `error` for `failure`, `failed`, or `cancelled`. |
| `version` | GitHub runtime metadata | The commit SHA supplied by `GITHUB_SHA`. |
| `attributes.repository`, `commit_sha`, `ref`, `workflow`, `run_id`, `run_attempt`, `run_url`, `actor` | GitHub runtime metadata | Taken from standard GitHub Actions environment values. |
| `attributes.deployment_status` | Workflow input | Defaults to `success`; it can be supplied from `${{ job.status }}`. |

The values `acme/orders`, `42`, and `abc123` were intentionally supplied when the Action was tested locally, so they are example data rather than information from your GitHub repository. A real GitHub-runner event will contain your repository, actual commit SHA, workflow name, and run URL.

## Event requirements

All producers must send:

- a unique `event_id`;
- ISO timestamps for `occurred_at` and `received_at`;
- `tenant_id`, `environment`, and stable `service` names;
- an allowed `source` and severity;
- a non-empty `event_type`; and
- an `attributes` object no larger than 16 KiB.

The ingestion API validates the event and replaces `received_at` with its own receipt time. It redacts attribute keys that look like credentials, including names containing `token`, `password`, `secret`, `api_key`, `authorization`, or `cookie`.

## Choosing configured values

Use a stable service name—`orders`, not a pod name or a GitHub run name. Use a small, consistent environment set such as `development`, `staging`, and `production`. Keep `tenant_id` aligned with the ingestion key; the current CLI creates keys for `local`.

These conventions keep deployment, application, and Kubernetes evidence joinable in the same incident timeline.

## Kubernetes workload events

The Kubernetes collector produces `source: "kubernetes"` events from a configured namespace. `service` comes from the Pod label `app.kubernetes.io/name` by default; unlabeled Pods are intentionally ignored so ephemeral Pod names do not become service identities.

`resource` identifies the affected workload as `pod/<namespace>/<pod-name>`, `deployment/<namespace>/<deployment-name>`, or `job/<namespace>/<job-name>`. The collector records the cluster name, namespace, workload name, Kubernetes reason, container when available, restart count when available, and a bounded diagnostic message. Its event IDs are deterministic, so watch reconnects and collector restarts do not duplicate evidence in the API.

See the [Kubernetes workload collector guide](integrations/kubernetes-collector.md) for its read-only RBAC manifest and configuration.
